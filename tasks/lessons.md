# Lessons

- ユーザーが「簡単なもの」と言った場合、実装の単純さを指すと決めつけず、直前の文脈にある利用体験・入力の簡単さを優先して解釈する。セキュリティ上の残余リスクは短く明示しつつ、選択自体はユーザーの優先順位に合わせる。
- ユーザーがローカルにある既存secretの再利用を明示した場合は、手入力を前提にせず、対象プロジェクト内の既存ソースを値非表示で探索してgitignore済みファイルへ安全に転記する。生成値は長さ・文字種・既存値との差分まで検証し、プラットフォーム固有コマンドの出力形式を思い込まない。
- ローカルにsecret値が存在することと、その資格情報が現在も有効であることは別。外部APIの認証を実行できる段階までは「転記済み」とのみ報告し、「再利用できる」「準備完了」と断定しない。
- プロジェクトの進捗を回答するときは`tasks/todo.md`だけを見ず、最新の作業ログ、実装計画のチェック状態、Git履歴、実ファイルを突き合わせる。別エージェントが後続フェーズを完了している可能性を先に確認してから「次のフェーズ」を案内する。
- 同じIssue番号が複数リポジトリに存在し得るため、番号だけで対象や内容を判断しない。このフォルダのIssueは`fukurose-jun02/fukuchan-app`で管理し、参照・更新・クローズ前にリポジトリ完全名を確認する。
- ユーザーが「どのフォルダでも同じ運用」と言った場合、直前の固有ルールの全体適用と決めつけず、ファイル構成・管理方式など抽象化された運用を指している可能性を確認する。今回は各プロジェクトで`AGENTS.md`を実体、`CLAUDE.md`をそのシンボリックリンクにする方式を共通化する。
- 実装を開始するときは、対象機能の要件定義書・設計書・実装計画書を先に読み、要件・設計・進捗・検証結果が変わるたびに開発文章と`tasks/todo.md`を同じ作業内で更新する。文章とコードがずれた状態を残さない。
- OAuthクライアントは単一scopeの認可リクエストでscopeパラメータを省略することがある。scope省略を不正と決めつけず、サーバーの既定scopeを明示的に適用し、明示された未対応scopeだけを拒否する。
- OAuth Providerの認可コード形式が内部の`userId`を区切り文字で連結する場合、`userId`へ同じ区切り文字を含めない。外部主体のprefixはスラッシュ等の安全な区切りへ分離し、実コード交換まで検証する。
- Geminiのfunction callingはRPC往復が成功しても最終合成で旧ナレッジやモデル知識を優先することがある。functionResponse後のsystem instructionで結果を唯一の根拠と明示し、架空データの往復テストで金額・期間・鮮度を検証する。
- Bearerトークンを端末から貼り付ける運用では、ANSI制御文字（`ESC[`）が混入するとCloudflare端でHTTP 400になり得る。秘密値はヘッダー安全な文字種で生成し、値を表示せず長さ・ASCII文字種だけを検証する。
